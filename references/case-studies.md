## GeekNews: 작은 서버로 캐시 계층 쌓기

출처: 권정혁(xguru), 「작은 서버로 큰 트래픽을 버티는 법」, 2026-08-07. https://hada.io/blog/geeknews-cache-on-a-budget/

**캐시 계층.** CDN(CloudFront) → Nginx 정적 HTML → Nginx 마이크로캐시 → 앱 캐시 → DB. 정적 HTML은 30일 넘은 토픽을 압축 파일로 둔 것이다. 사이트맵과 오래된 아카이브 조회 결과도 미리 파일로 만든다.

**개인화 분리.** 예전에는 로그인 쿠키가 있으면 캐시를 우회했다. 로그인 상태, 투표, 즐겨찾기를 페이지 로드 뒤 부르는 별도 API로 옮겼고, 브라우저가 최근 상태를 잠깐 기억해 먼저 보여준다. 헤더에 아이디와 카르마를 찍던 자리는 공통 사람 아이콘과 팝업 메뉴로 바꿨다.

**TTL.**

| 대상 | TTL |
|---|---|
| 첫 화면, 새 글, 1일 미만 글 | 수십 초 |
| 토픽 1~3일 | 1분 |
| 토픽 3~30일 | 1시간 |
| 토픽 30일 이상 | CDN 24시간 + 정적 HTML |
| 아카이브 7일 미만 | 3분 |
| 아카이브 7~30일 | 1시간 |
| 아카이브 30일 이상 | 24시간 |

**적중률.**
- 첫 화면과 새 글 목록은 15초 TTL로 70% 후반.
- 30일 미만 글 전체에 15초 TTL을 줬을 때: 1~3일 글 38.0%, 3~30일 글 10.6%. 다시 요청되는 간격이 TTL보다 길었다.
- 오래된 글: 하루 1회 읽히는 글 22.5%, 하루 50회 이상 읽히는 글 96.5%. 매일 읽히는 오래된 토픽은 약 1만 6천 개이고 그중 절반 정도가 하루 한 번만 읽힌다.
- 오래된 글의 CDN TTL을 1시간에서 24시간으로 늘리자 58~59%에서 79.0%로 올랐다.
- 30일 넘은 날짜별 아카이브는 아카이브 요청의 약 81%였지만 적중률은 0.8%였다.
- 한때 CloudFront 전체 적중/미스는 대략 반반이었다.

**측정.** 페이지를 열 때마다 조회수를 DB에 쓰면 서비스가 느려지므로, CloudFront 로그를 별도 기기에서 배치로 처리한다. 오래된 노트북이 작은 EC2 인스턴스보다 나았다. 날짜, 페이지 종류, 기기, 캐시 결과, 토픽 나이별 집계만 남긴다.

**작은 서비스가 따라 할 순서.**
1. 비싼 공개 GET 찾기 (접근 로그와 앱 처리 시간)
2. 그 요청에 세션이 정말 필요한지 확인
3. 15초 마이크로캐시
4. 캐시 키 정규화
5. 바뀌는 빈도에 따라 URL 나누기
6. 정확한 무효화 (CDN TTL은 짧게 시작)
7. 적중률을 페이지 종류와 나이로 쪼개 보기

**참고.** 원문은 백엔드 언어나 DB를 밝히지 않는다. 2021년 댓글 기준으로는 PHP + MySQL, AWS였다고 알려져 있지만 현재도 같은지는 확인되지 않았다.

**이 스킬에 반영한 곳.** `caching.md` 3~8절, SKILL.md 실행 체크리스트.

## X.com: 웹 클라이언트 재구축

출처: Yagiz Nizipli, "Rebuilding the global town square from scratch", X Engineering 블로그, 2026-11-04. https://blog.x.com/en/engineering/rebuilding-the-global-town-square-from-scratch

**범위.** 서버 3개(rweb, rweb SSR, Jetfuel SSR)를 하나로 합쳤다. 엔지니어 5명 안팎(글 안에서 "5명"과 "5명 미만"이 둘 다 나온다)과 AI 에이전트로 6개월 안에 첫 버전을 만들었다. Jetfuel SSR은 2026-08-01에, rweb SSR은 9월 초에 내렸다.

**스택.** Vite(Rolldown), React 스트리밍 SSR + Suspense, Fastify, Platformatic Watt(Node.js 26, 워커 스레드), Relay + GraphQL, Tailwind, Base UI 기반 자체 컴포넌트 라이브러리(XDS), 타입 검사용 tsrs(TypeScript 컴파일러의 Rust 포트).

**결과.**
- Slow 4G 녹화에서 첫 게시물: 기존 23.9초, 새 앱 2.7초.
- 로그인 상태, 느린 프로파일의 첫 게시물 시간:

  | 페이지 | 기존 | 새 앱 | 개선 |
  |---|---|---|---|
  | 게시물 | 약 22~25초 | 1.7초 | 12.8배 |
  | 프로필 | 약 22~25초 | 3.0초 | 8.2배 |
  | 홈 | 24.6초 | 14.1초 | 1.7배 |

  홈은 아직 CSR이라 개선 폭이 가장 작다. 스로틀링 없이 재면 게시물 3.2배, 프로필 2.3배, 홈 1.2배다.
- TTFB는 300ms 미만에서 430~560ms로 늘었다. 첫 콘텐츠 전 JS 다운로드는 게시물과 프로필에서 3.0~3.6MB에서 0MB가 됐다(홈은 여전히 1.9MB). 전체 JS는 4.1~4.8MB에서 1.3~2.3MB.
- 비로그인 인스턴스는 데이터센터당 1,400개에서 700개로 줄었다.

**최적화 항목.**
- 초기 JS 파일 수: 로그인 754개 → 182개, 비로그인 582개 → 10개. JS 응답마다 275ms 지연을 준 시험에서 홈 6.63초 → 4.95초.
- CSS 우선 로딩: 비로그인 프로필 FCP 3,064ms → 1,984ms, 게시물 7,216ms → 1,804ms. 대신 5개 페이지 중 2개에서 하이드레이션 완료가 0.3%, 0.6% 늦어졌다.
- `async` 모듈 하이드레이션: 서버에 5초 지연을 넣은 시험에서 React 연결 589ms, 문서 파싱 완료 6,017ms.
- Relay 스토어 직렬화를 원본 GraphQL 응답 JSON으로 교체. 스토어 레코드가 원본의 4~5배였다.
- 게스트 토큰과 기능 플래그 요청 병렬화.
- 이벤트 루프 지연으로 생긴 가짜 타임아웃: 상위 서비스는 약 25ms에 답했는데 비로그인 렌더의 1~9%에서 1초 타임아웃이 났다. 이벤트 루프는 중앙값 67%, p95 84% 시간 동안 바빴다. 워커를 늘려 해결.
- 크롤러용 HTML을 2MB 이하로(긴 스레드는 2.2~3.5MB였다): SVG 스프라이트로 165KB(프로필, 14.2%)와 340KB(긴 스레드, 13.6%), 구조화 데이터 중복 제거로 450KB(13.0%), JS 전용 출력 제거로 54KB(137개 게시물 스레드).
- 바이트 줄이기: 영어 카탈로그 49.5KB(gzip) 제거, ICU 파서 교체로 진입점마다 약 8KB, 211개 청크에 들어 있던 Sentry release ID 12.4KB, 이미지 WebP 전환.
- 화면 전환: 링크는 hover나 focus에, 타임라인 게시물은 포인터가 100ms 머물거나 누를 때 미리 받는다.

**운영.** parity 스크립트로 기존 서버와 응답을 비교했다. ngroutes로 엣지에서 경로별 라우팅을 하고, 기능 스위치로 즉시 되돌릴 수 있게 했고, 국가별로 전환했다. Money, X Chat, Calls는 Module Federation으로 불러오며 Money 첫 페이지가 590KB → 509KB(gzip)가 됐다.

**AI 에이전트 운영.** AGENTS.md, 25개 이상의 스킬, oxlint 커스텀 플러그인과 anti-slop 플러그인, pre-commit/pre-push 훅.

**교훈.**
- 기존 시스템이 가장 좋은 명세다.
- 점진 전환과 즉시 복귀가 안전을 만든다.
- 실험실 수치와 실사용 수치를 함께 본다.

**이 스킬에 반영한 곳.** `rendering.md`, `frontend.md` 4~6·9~11절, `backend.md` 1·4절, `migration.md`.
